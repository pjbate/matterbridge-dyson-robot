# RB05 installation and use

This is the experimental `1.10.17-rb05.12` fork, not the current official plugin. It replaces the installed `matterbridge-dyson-robot` package. Read the [scope and test evidence](VALIDATION.md) first.

## Before installing

1. Check whether the current [official plugin](https://github.com/thoukydides/matterbridge-dyson-robot) already meets your needs.
2. Complete mapping and configure each room's cleaning rules in MyDyson. This fork leaves those rules in the robot.
3. Keep a recoverable copy of your current plugin package and the Matterbridge data/configuration directory, including pairing state. Keep that backup private: it can contain account credentials.
4. Stop Matterbridge using the mechanism that normally runs it. Do not run a second instance or delete pairing data.
5. Download this fork's release `.tgz` and its checksum file. Verify the package's SHA-256 before installing.

The live-tested environment was Windows, Node 24.18.0, Matterbridge 3.10.6 and Matter.js 0.17.9. The public build is offline-tested against Matterbridge 3.10.12 with the same Matter.js version. It requires Matterbridge 3.10.12 or later to avoid recommending the older host version with inherited security advisories. Do not downgrade your host to the historical live-test version. Other versions are not a compatibility guarantee.

## Install the downloaded package

Run this from the same account and npm installation prefix used by Matterbridge, substituting the actual local package path:

```sh
npm install -g "/path/to/matterbridge-dyson-robot-1.10.17-rb05.12.tgz"
```

On Windows the argument should be the downloaded file's Windows path. The quotes are important if it contains spaces. Use your existing service/task controls to stop and restart Matterbridge; do not change the service account just for this package.

If the plugin is not already registered:

```sh
matterbridge -add matterbridge-dyson-robot
```

For an existing installation, do not remove/re-add the plugin or reset commissioned Matter devices. Restart Matterbridge after replacement. Confirm the plugin reports version `1.10.17-rb05.12`.

Use the existing plugin configuration and its normal MyDyson authorisation flow. The RB05 connection tested here uses `Remote Account`, not an unauthenticated local-network connection. Do not put tokens or passwords in issue reports.

Keep `enableServerRvc: true` for the tested Apple Home layout. Keep `unregisterOnShutdown: false` for normal use.

## Pair and create a room scene

1. Pair the Matterbridge bridge in Apple Home. This exposes the momentary room tiles.
2. With `enableServerRvc` enabled, pair the standalone robot using that device's separate QR code. This exposes robot status, Pause and Return to dock.
3. Verify each room tile matches a room on the current MyDyson map.
4. Create a Home scene containing only the intended room tile, set to Turn On.
5. Give the scene the phrase you want to use with Siri, such as “Clean Room A”.

A room button uses the saved Dyson rule, whether that is vacuum-only or a wet-cleaning rule. “Mop” in a scene's name is only a label. This fork does not force a mopping override.

For the first test, supervise the robot with its path clear. Confirm the physical target room and the expected cleaning behaviour. Stay available until it finishes and returns to the dock. Do not treat a successful Matter request as proof that the physical room has been cleaned.

## Button and status behaviour

Turning a room tile On requests one room clean. After the robot supplies a fresh accepted running state, the tile pulses On and then resets Off after about one second. This is an acknowledgement, not an indication that cleaning has finished.

Turning a tile Off only resets its display. It never sends Stop or Abort. Use the main robot controls to Pause or Return to dock.

Starting a room is refused if the robot is unreachable, disconnected, busy, paused, locked, has a non-log-only active fault, cannot supply fresh full state or cannot resolve the same room on its current map. Repeated presses are not queued. A reported whole-home fallback to an attempted room start is rejected and a compensating abort is attempted.

For safety, room identity uses robot, map and zone IDs rather than room names or array order. Renaming a room cannot silently turn an existing tile into a different room. Restart Matterbridge after adding or renaming rooms so the tile list and labels are rebuilt. Map changes and removal may make old tiles unavailable; check and rebuild affected Home scenes.

Reported activity includes finding location, vacuuming, vacuuming and mopping, mopping, travelling to a room, returning to dock, charging, dust emptying and mop washing/drying. Unsupported or unknown activity falls back to an honest generic state. No room progress percentage or completion time is invented.

Apple Home may display generic wording for those standard Matter fields. Use the bridge log and MyDyson for detailed troubleshooting.

## If Home reports failure

Do not repeatedly press different room tiles. Confirm the robot is idle, the bridge is running and MyDyson can reach it. Check for fresh-state timeouts and map/room validation errors in the bridge log.

During development, some fresh-state timeouts occurred while additional MQTT observers were connected. A later attempt succeeded after those observers were stopped and Matterbridge restarted. This is a correlation, not a confirmed cause or a promise that restart fixes every failure.

Keep only the normal bridge connection while reproducing a problem. Do not disable safety checks or assume a broker acknowledgement means that the robot accepted the job.

## Roll back

Stop Matterbridge, reinstall your saved previous plugin package with the same account and npm prefix, then restart Matterbridge. Restore your private data/configuration backup only if needed and after preserving the current copy.

Do not delete pairing state as part of a normal package rollback. Earlier versions may not expose room tiles, so scenes using those tiles can stop working. Keep MyDyson available as the normal fallback.

Automatic service startup and Windows reboot recovery are deployment concerns, not configured by this package. Check the service or scheduled task used by your own installation.
